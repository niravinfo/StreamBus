In this article, you learn what happens between `RunAsync` and the
first delivered message: how startup can block or stay backgrounded,
what happens when the broker disappears, and how each call site
states its patience.

`AddStreamBus` registers a hosted service — there is nothing else to
add, and no separate "start the bus" call. Startup and shutdown
behavior is configured through the standard options pattern:

```csharp
builder.Services.AddOptions<StreamBusHostOptions>().Configure(o =>
{
    o.WaitUntilStarted = true;
    o.StartTimeout = TimeSpan.FromSeconds(30);
});
```

## Startup: non-blocking by default

By default (`WaitUntilStarted = false`, the default), host startup
does not wait for the broker: connections, declarations, and consumer
attaches continue in the background while the application serves
traffic. Permanent background failures are logged critically, and the
`streambus` health check reports the truth — `Degraded` while
starting or retrying:

- containers and orchestrators waiting on health checks hold traffic
  correctly without the process blocking its own startup;
- a broker that is down at deploy time doesn't prevent the
  application from booting.

This is deliberate parity with how modern message libraries behave;
blocking startup is opt-in for the cases that want crash-early.

## Startup: blocking opt-in

Set `WaitUntilStarted = true` to make `RunAsync` wait until every bus
connection is ready and topology is declared — and, unless disabled,
until all typed consumers are attached:

| Option | Default | Meaning |
|---|---|---|
| `WaitUntilStarted` | `false` | Block startup on bus readiness. |
| `StartTimeout` | `null` | Budget for the blocking wait; `null` waits indefinitely (host shutdown always unblocks it, so there is no deadlock). A set budget throws `StreamBusTimeoutException` on expiry. |
| `WaitUntilConsumersAttached` | `true` | When blocking, also wait for every typed consumer to attach. A consumer that can't attach retries indefinitely; the wait ends on the timeout, not on the first consumer failure. |

## Readiness policies: per call-site patience

Independently of hosting, every operation that touches the wire takes
a `ReadinessPolicy` for "how long do I wait for the broker to be
ready?":

- `ReadinessPolicy.Default` — fail fast, throwing
  `StreamBusNotReadyException` (this is the publish default);
- `ReadinessPolicy.UpTo(timeout)` — bounded wait;
- `ReadinessPolicy.Forever` — wait until ready or cancelled.

```csharp
// Publish: fail fast if the connection is down (the default).
await bus.PublishAsync(new OrderPlaced("o-1"), ct);

// Publish: wait up to ten seconds for a connection instead.
await bus.PublishAsync(new OrderPlaced("o-1"), new PublishOptions
{
    Readiness = ReadinessPolicy.UpTo(TimeSpan.FromSeconds(10)),
}, ct);
```

Endpoints take the same policy for their attach via
`e.Readiness(...)`, and `bus.WaitUntilReadyAsync(policy, ct)` lets
code gate itself explicitly, for callers who need the connection but
not the bus (the health check stays the orchestration-facing signal).
The policy bounds the *readiness wait only* — the broker-confirmation
wait on a publish is a separate `ConfirmTimeout`.

## When the broker disappears mid-flight

Each bus owns a connection supervisor that keeps the broker
connection and reports a live state — visible on `IStreamBus.State`
and on the [health check](../observability/):

| `BusConnectionState` | Meaning |
|---|---|
| `Starting` | First connection attempt in flight. |
| `Ready` | Connected; producers and consumers operate. |
| `TransientFailure` | A transient failure occurred; reconnecting with backoff. Publishes surface `StreamBusPublishTransientException`; the endpoint detaches and reattaches. |
| `Fatal` | Unrecoverable — protocol, TLS, or authentication failure. No automatic retry; operator action required. |

After a reconnect, consumers resume from their consumer group's
stored offset — plus, per [Architecture](../architecture/), a
redelivered tail from wherever the stored cursor trailed the live
one.

## Shutdown

`StopAsync` disposes consumers first, then cancellation of any
in-flight startup, then connections — each step individually
budgetable:

| Option | Default | Meaning |
|---|---|---|
| `StopTimeout` | `null` (indefinite) | Overall shutdown budget; on expiry, remaining steps are abandoned with warnings. |
| `ConsumerStopTimeout` | `null` (unbounded) | Per-consumer `DisposeAsync` budget; may be set on its own. |

```csharp
builder.Services.AddOptions<StreamBusHostOptions>().Configure(o =>
{
    o.StopTimeout = TimeSpan.FromSeconds(20);
    o.ConsumerStopTimeout = TimeSpan.FromSeconds(5);
});
```

Validation: every timeout must be positive when set, and
`ConsumerStopTimeout` must not exceed `StopTimeout` when both are set;
violations throw `StreamBusConfigurationException` at host start/stop.
