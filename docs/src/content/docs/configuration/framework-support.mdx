---
title: Framework support
description: Which StreamBus asset a .NET app resolves, and how runtime async is decided.
---

StreamBus ships **one NuGet package with two compiled assets**. Your app resolves the right one automatically; no configuration or package change is needed.

## Support matrix

| Your app's target framework | Resolved asset | Notes |
| --- | --- | --- |
| `net10.0` | `lib/net10.0/StreamBus.dll` | The original asset. Behavior is unchanged from earlier StreamBus releases. |
| `net11.0` | `lib/net11.0/StreamBus.dll` | Natively compiled for .NET 11. |

NuGet picks the closest compatible asset. Both assets expose the same public API, so moving an app from .NET 10 to .NET 11 does not change any StreamBus call site.

## Runtime async

.NET 11 introduced runtime-native async. The `net11.0` StreamBus asset may be compiled with it; the `net10.0` asset never is (the feature requires a .NET 11 target).

The decision belongs to **the assembly being compiled, not the app running it**:

- Your project's `<Features>$(Features);runtime-async=on</Features>` affects only code compiled in **your** project.
- Turning it off in your project does **not** recompile StreamBus. If the net11 StreamBus asset was built with runtime async, your app still calls those runtime-async methods.
- Likewise, a .NET 10 app is unaffected — it resolves the net10 asset, which cannot use runtime async.

This is a behavioral change worth knowing about when reading stack traces. A live stack captured inside a runtime-async method shows the real method name rather than state-machine frames (`MoveNext`). A thrown exception still points at the same source line, but its top frame may show the real method name instead of the generated state-machine type. `AsyncLocal<T>` values flow across `await` the same way in both modes.

## .NET 11 hardware baseline

.NET 11 raises its minimum CPU baseline to `x86-64-v2` (and `LSE` on Arm64 Windows). If you deploy StreamBus on older VMs or container hosts, verify the host meets the .NET 11 baseline before upgrading an app to `net11.0`. A .NET 10 app is not affected by this change.
